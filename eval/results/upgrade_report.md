***REMOVED******REMOVED******REMOVED*** 2.6 诚实说明与局限

- **表格问答仍是短板**（准确率 62.5%）：对比类问题需要跨行推理（"哪款功率最大"），检索能命中表格块但生成端单跳抽取易错。改进方向：重排序 + 表格问答专用提示词/行列序列化增强。
- **引用校验未在本次评测中触发**：全部配置 citation_valid_rate=100%、重生成 0 次——判分模型对编号规则服从良好；校验与重生成机制由单元测试覆盖（伪造编号 [9]/[0] 检测、降级重生成路径）。
- 评测期间 API 免费配额三次耗尽（qwen3.5-flash → qwen3.6-35b-a3b → deepseek-v4-pro），最终除 smart_vector 生成结果外，全部配置由 deepseek-v4-pro 统一判分（见 2.2 脚注）；baseline 有 5 题生成失败按 0 分计入（占比 2.9%，对结论无实质影响）。
- 忠实度/相关性/判分与被测同源（同一 LLM），存在自判偏差；语料为程序化生成的企业文档，真实语料上的绝对数值会低于本报告。

***REMOVED******REMOVED*** 三、混合检索深度调优（`tune_retrieval.py`，156 道单轮题）

***REMOVED******REMOVED******REMOVED*** 3.1 RRF 网格搜索（score = Σ 1/(k+rank)^p）

- 16 组合中**最优 k=10, p=3.0**：Recall@5 99.4%、MRR 0.910（默认 k=60, p=1.0：98.7% / 0.900）；
- 结论：k 越小、p 越大，头部排名权重越大，对本语料头部命中更有利；差异幅度小（+0.7pp R@5），已在配置中保留可调参数（`RRF_K`/`RRF_P`）。

***REMOVED******REMOVED******REMOVED*** 3.2 BM25 分词变体（最优 RRF 参数下）

| 变体 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|
| precise（精确模式） | 98.1% | 99.4% | 0.910 |
| precise_dict（+自定义词典） | 98.1% | 99.4% | 0.910 |
| search（搜索引擎模式） | 97.4% | 99.4% | **0.917** |
| search_dict | 97.4% | 99.4% | 0.917 |

自定义词典（型号/缩写/术语 50+ 词条）在准确率上与默认持平——本语料的专名（C3、X7、AQL、RRF）jieba 已可切分；词典价值预期在专名更密集的真实语料。搜索引擎模式 MRR 略优（细粒度切分提高头部重合），默认采用 `precise_dict`（稳健折中）。

***REMOVED******REMOVED******REMOVED*** 3.3 LLM 查询扩展（负结果，如实报告）

| 设置 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|
| off | 98.1% | 99.4% | 0.910 |
| on | 97.4% | 99.4% | 0.904 |

扩展词引入噪声词稀释了 BM25 与向量排序，**Recall@3 下降 0.7pp**。结论：在语料小、检索已接近饱和时扩展无益；`EXPAND_QUERY` 默认关闭，保留开关供大规模语料复测。

***REMOVED******REMOVED*** 四、性能与规模化基准

***REMOVED******REMOVED******REMOVED*** 4.1 规模基准（1000 篇模拟文档，纯 CPU）

| 指标 | 数值 |
|---|---|
| 语料规模 | 1000 篇 / 5000 chunks（693KB 文本） |
| 首次入库（解析+切分+编码+双索引） | **199.7s**（≈25 chunks/s；第二次测量 255.3s，当时与评测任务并发，取为上限） |
| **增量入库（MD5 未变）** | **1.25–1.37s**（1000/1000 篇全部跳过，**≈150 倍加速**） |
| 检索延迟（向量+BM25+RRF，不含 LLM） | **P50 65–84ms / P95 82–109ms** |
| 进程内存 | 118MB → 957–1044MB（主要为嵌入模型与索引） |

***REMOVED******REMOVED******REMOVED*** 4.2 嵌入编码加速（256 条文本 × 3 次取最优）

| 后端 | 吞吐 | 相对 PyTorch |
|---|---|---|
| sentence-transformers (PyTorch) | 35 条/s | 1.00× |
| ONNX Runtime fp32 | 30 条/s | 0.86×（更慢） |
| **ONNX Runtime int8（动态量化）** | **51 条/s** | **1.47×** |

结论：fp32 ONNX 不值得（torch CPU 已高度优化）；**int8 动态量化提速 1.47×** 且导出为一次性成本（脚本自动缓存 `data/.cache/text2vec-int8.onnx`），大规模入库时可切换。

***REMOVED******REMOVED******REMOVED*** 4.3 大规模索引方案

- **≤10 万块**：Chroma 单集合 + HNSW 余弦可满足（5000 块 P50 65ms，规模线性外推 10 万块仍在百毫秒级）；
- **>10 万块**：提供 `scripts/migrate_to_milvus.py`（HNSW COSINE 索引、批量迁移、元数据全保留）；Chroma 多集合按文档哈希分片方案已在代码中预留 `COLLECTION_NAME` 维度。

***REMOVED******REMOVED*** 六、结论

1. **消融证据链完整**：智能切分（R@5 +12.8pp）、混合检索（R@5 +4.7pp，p=0.006）、多轮改写（多轮题准确率 +12.5pp）三个模块的独立贡献均在扩大的 206 题评测上量化，主对比在 95% CI 下显著。
2. **端到端准确率 74.4% → 93.6%**，忠实度 0.999、拒答正确率 100%、段落级溯源 97.7%——升级后的系统在"答得准、可追溯、不编造"三个维度同时达标。
3. **负结果同样入册**：LLM 查询扩展在本语料上无收益；表格跨行对比问答仍是短板；引用校验在评测中未被触发（机制由单测保证）。这些发现为下一阶段（重排序、表格问答增强）提供了明确方向。
4. **工程可用性**：增量入库 150 倍加速、int8 编码 1.47×、P95 检索 <110ms、Milvus 迁移路径就绪，系统具备向 10 万块级语料扩展的工程基础。
